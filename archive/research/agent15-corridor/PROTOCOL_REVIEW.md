# 한 대 전용 통로 진입 프로토콜 검토

조사일: 2026-10-14. 범위: 공식 문서 및 공개 원본 소스 읽기, 설계 검토. 제품 코드·배포·서비스·실물 로봇은 변경하거나 시험하지 않았다. 아래 프로토콜과 시험표는 학생 프로젝트를 위한 제안이며 구현 완료 또는 산업 안전 인증을 뜻하지 않는다.

## 결론

사용자의 QR 아이디어는 통로를 식별하는 출발점으로 타당하다. 필요한 규칙은 **QR을 읽고 진입을 요청한 뒤, 유일한 중재자가 확정한 허가를 받은 한 대만 들어간다**이다. QR을 먼저 읽었다거나 소유권을 방송했다는 사실만으로 진입권이 생기지는 않는다. 기다리는 로봇은 넓은 입구 대기구역에서 기다리므로 무조건 우회할 필요가 없다.

이번 전제는 한 통로 안에 어떤 방향이든 로봇이 최대 한 대만 존재하는 것이다. 같은 방향의 뒤따르기도 허용하지 않는다. 후진·옆걸음·제자리회전은 금지한다. 자동차식 전진 U턴은 차체와 적재물 전체가 지나갈 회전 공간에서만 허용한다.

## 구분해야 할 문제

| 문제 | 정확한 뜻 | 필요한 대책 |
|---|---|---|
| 상호배제 | 같은 통로에 동시에 두 대가 들어가지 않음 | 통로별 단일 확정 소유권과 진입 전 허가 |
| 충돌 정지 | 예상 밖 사람·물체가 나타났을 때 부딪히기 전 멈춤 | 센서·제동·로컬 정지 제어 |
| 교착 방지 | 각자 공간을 차지한 채 서로의 공간을 기다리는 순환이 없음 | 출구 대기공간 예약, 대기 위치 설계, 자원 의존성 검사 |
| 공정성 | 계속 요청하는 특정 로봇이 영원히 밀리지 않음 | 접수 순번, 오래 기다린 요청 우선, 제한된 추월 |
| 주행 가능성 | 후진 없이 출구와 다음 정차 지점에 도달 가능 | 전진 방향 그래프와 차체의 회전 궤적 검증 |

이 구분은 본 시나리오에 대한 설계 분석이다. Open-RMF의 공식 Graph API도 mutex group으로 묶인 waypoint/lane에 한 번에 한 로봇만 점유할 수 있다고 설명한다. 이 개념이 여러 자원에 걸친 모든 교착이나 물리적 충돌까지 자동 해결한다는 뜻은 아니다. [Open-RMF Graph::Waypoint API](https://docs.ros.org/en/rolling/p/rmf_traffic/generated/classrmf__traffic_1_1agv_1_1Graph_1_1Waypoint.html)

## QR과 진입선 배치

- QR의 내용은 예컨대 mapVersion, aisleId, entranceId, direction이다. 서로 반대편 입구 QR도 동일한 aisleId 자원을 가리켜야 한다. 각 랙마다 독립 자원으로 쪼개면 같은 좁은 통로의 양끝에 각각 허가할 수 있다.
- QR은 위치·자원 식별을 돕는다. 통로 비어 있음, 유효한 허가, 퇴장 완료를 QR 하나가 보증하지 않는다.
- 진입선을 넘기 전에 차체 전체를 세울 수 있는 위치에서 요청한다. 아직 허가가 없으면 진입선 앞에서 반드시 정지한다. QR 인식 시점이 너무 늦으면 이미 제동할 공간이 없어질 수 있다.
- 회전과 차량 길이, 적재물까지 포함한 swept footprint로 통로 입구·출구·대기 위치의 겹침을 판단한다. 출구 센서나 QR을 로봇 앞쪽이 지났다는 이유로 즉시 해제하지 않고 후미까지 빠져나왔음을 확인한다.

정지거리의 참고 형식은 d = v·반응시간 + v²/(2·감속도) + 여유거리다. 실제 속도·지연·제동 성능과 위치 오차를 측정해야 수치가 정해진다. Nav2 공식 튜토리얼도 속도별 정지 영역과 이 형식을 설명한다. [Nav2 Collision Monitor 튜토리얼](https://docs.nav2.org/rolling/tutorials/general_tutorials/using_collision_monitor/using_collision_monitor/)

## 최소 권장 구조

학생 4명 프로젝트의 첫 실험은 **로컬 중재 프로세스 1개 + 로봇별 상태기계 + 선택적 MQTT 전달**로 충분하다. MQTT broker와 중재자는 서로 다른 역할이다. broker는 메시지를 전달하고, 중재자는 어떤 요청 하나를 채택할지 판단하고 저장한다. 같은 PC에서 실행할 수 있지만 논리적으로 구분한다.

원자적 처리는 현재 FREE 여부 확인과 RESERVED 기록을 하나의 직렬 처리로 묶는다는 뜻이다. 단지 각 로봇이 FREE 방송을 보고 자기 소유라고 다시 방송하는 방식은 이 동작을 제공하지 않는다. 중재자는 허가 상태를 영속 기록한 뒤 GRANT를 보낸다. 기록 실패 시 허가하지 않는다. 중재자 하나가 고장나면 새 진입을 멈추는 단순 구성이, 확인되지 않은 자동 이중화보다 이 실험 범위에 적합하다.

| 이벤트 | 최소 의미 | 처리 기준 |
|---|---|---|
| REQUEST | 이 통로와 출구 정차공간을 쓰고 싶음 | robotId, bootId, requestId, resourceId, direction을 식별 |
| GRANT | 특정 요청에 대한 확정 허가 | 중재자가 소유권을 저장한 후 발급. 예약과 일치하는 로봇만 진입 |
| ENTER | 허가받은 로봇이 진입선을 넘음 | 현재 허가 식별자와 일치할 때 OCCUPIED로 전이 |
| EXIT | 차체·적재물 후미까지 통로를 벗어남 | 같은 소유자의 동일 허가에만 해제 적용; 출구 berth 점유는 별도로 유지 |
| FAULT | 통신·위치·동작 상태가 불확실 | 신규 진입 금지, 재확인 전 UNKNOWN/BLOCKED 유지 |

이는 프로젝트용 이벤트 이름이며 VDA5050 표준 메시지 이름을 그대로 구현했다는 뜻은 아니다. 상태는 FREE → RESERVED → OCCUPIED → FREE이며, 허가 후 불확실한 경우 UNKNOWN/BLOCKED로 빠진다. **GRANT를 받은 뒤 ENTER가 안 왔다고 다른 로봇에 재발급하면 안 된다.** 먼저 받았던 로봇이 이미 진입했거나 지연된 허가로 앞으로 진입할 수 있다.

허가에는 resourceId, robotId, bootId, requestId, coordinatorEpoch, grantSequence를 넣는다. 재전송은 같은 requestId로 하며 중복 요청에 새 허가를 만들지 않는다. 늦은 EXIT가 새 소유권을 해제하지 않게 전체 허가 식별자를 비교한다. 로봇 재부팅 후에는 기존 허가를 독자적으로 재사용하지 않는다. 중재자 재시작 후에는 저장된 소유권을 복원하고 점유를 재확인한다. 새 epoch 번호만 붙인다고 실제 통로에 남은 옛 로봇이 사라지지 않는다. 이 원칙은 설계 제안이며 위 표만으로 완성된 장애 복구 프로토콜은 아니다.

MQTT QoS 0에서는 유실이, QoS 1에서는 중복이 가능하다. 동일 publisher의 순서 규칙을 여러 로봇 요청에 대한 전역 우선순위로 확대해서 해석하면 안 된다. QoS 2 역시 물리적 통로 소유권을 원자적으로 배정하는 알고리즘은 아니다. [OASIS MQTT 5.0, §4.3 및 §4.6](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html)

## 방송만으로 해결되지 않는 반례

1. A와 B가 양끝 QR을 거의 동시에 읽는다.
2. 두 로봇 모두 아직 다른 로봇의 점유 방송을 못 받았다.
3. A는 A 소유, B는 B 소유라고 각각 방송하고 진입한다.
4. 늦게 상대 방송을 받았을 때 이미 통로 안이다. 정지해도 후진이 금지되어 대치한다.

패킷을 잃거나 네트워크가 둘로 갈라져도 같은 문제가 발생한다. '상대에게서 답이 없으면 내가 간다'는 규칙은 이 조건에서 사용할 수 없다. '1 cm 먼저 도착'도 서로 다른 위치 오차, QR 검출 시간, 시계 오차, 네트워크 지연 때문에 양쪽이 일치해서 판단하기 어렵다. 중재자의 접수 순번과 동률시 robotId 같은 결정 규칙으로 처리하되, 이것을 실제 물리적 선착순의 완벽한 측정이라고 부르지 않는다.

중앙 없이도 분산 상호배제 설계는 가능하다. 다만 멤버십, 모두가 합의한 요청 순서, 허가 응답 또는 유일 토큰, 재부팅, 토큰 분실, 네트워크 분할 처리가 추가된다. 단절 상태에서는 허가를 보수적으로 중단해야 하며, 임의 timeout 뒤 각자 리더·토큰을 만들면 두 소유자가 생길 수 있다. 학생 프로젝트의 2차 비교 실험으로는 가능하나 최초 최소 구현보다 범위가 크다.

## 통신 끊김과 시간 만료

heartbeat는 통신 상태를 추정하는 자료다. 통신이 끊겼다고 로봇이 통로에서 없어지는 것은 아니다. OCCUPIED 또는 발급된 허가의 행방이 불명확하면 신규 진입을 막고 실제 점유·허가 소멸을 확인한다. 미진입 예약을 취소할 때도 늦은 GRANT를 받은 로봇이 나중에 들어오지 못함을 확인하는 취소·동기화 과정이 필요하다.

VDA5050 3.0.0은 broker 연결이 끊겨도 마지막 released node까지 기존 명령을 수행한다고 정한다. §6.9는 REQUESTED/QUEUED/GRANTED 등 요청 응답과 선택적 leaseExpiry를 정의하지만, 만료 시 정해진 releaseLossBehavior를 수행하는 것과 통로가 비었다는 사실은 다르다. 이 규격은 교통 알고리즘과 안전 요구 자체를 범위에서 제외한다. [VDA5050 3.0.0 공식 고정본, §2·§4.1·§6.9](https://raw.githubusercontent.com/VDA5050/VDA5050/3.0.0/VDA5050_EN.md)

주의할 실제 구현 차이도 있다. 확인한 Open-RMF upstream main의 mutex supervisor는 heartbeat를 주기적으로 검사하여 10초가 지난 claim을 지우고 다음 소유자를 고를 수 있다. 따라서 본 보고서의 '불확실하면 닫아 두기'를 Open-RMF 기본 동작이라고 설명하면 틀린다. 채택 시 정확한 버전과 adapter 동작을 함께 검증해야 한다. [Open-RMF mutex_group_supervisor 공개 소스](https://raw.githubusercontent.com/open-rmf/rmf_ros2/main/rmf_fleet_adapter/src/mutex_group_supervisor/main.cpp)

## 출구를 막으면 한 대씩만 진입해도 교착한다

A가 통로를 점유하고 나가려는데 B가 출구 바로 앞에서 기다린다면 A는 EXIT를 못 보낸다. B는 A가 나가야 자기 허가를 받는다. A만 통로 안에 있어도 교착이다. 그래서 입구 대기 위치는 다른 방향의 출구와 회전 궤적을 막지 않아야 한다. 진입 허가 전에 통로뿐 아니라 **통로 밖에서 차체 전체가 서 있을 출구 berth 및 필요한 회전 공간**도 확보한다.

여러 통로가 이어지면 A가 X를 잡고 Y를, B가 Y를 잡고 X를 기다릴 수 있다. 최소 실험에서는 안전 대기공간까지 필요한 자원을 한 번에 확보하고, 확보하지 못하면 이전 안전 위치에서 기다리는 방식을 권한다. 더 큰 지도에서는 이미 점유한 위치까지 포함한 자원 의존 그래프와 순환 대기 방지 규칙을 검토해야 한다. '출구 하나 예약'만으로 모든 지도에서 교착 없음이 증명되지는 않는다.

후진 금지 조건에서 막다른 좁은 통로 끝에 전진 U턴 공간이나 연결 출구가 없다면 왕복 작업 자체가 불가능하다. 이는 통신이나 AI 판단으로 고칠 수 없는 기하 제약이다. 지도를 통과형으로 바꾸거나 실제 회전 반경을 만족하는 회차 공간을 두어야 한다. 회차 공간이 있더라도 좁은 통로 내부에서 모든 작업과 회차를 마치고 입구로 돌아올 때까지 통로 소유권을 유지한다.

## 학생 4명 최소 연구 범위와 검증표

| 담당 | 연구 산출물 |
|---|---|
| 1 | 전진 주행·회전 반경·차체/적재물 footprint·입출구 선·대기 위치 모델 |
| 2 | QR/resource 식별, REQUEST/GRANT 로봇 상태기계, 메시지 재전송 |
| 3 | 단일 중재자, 예약/점유 장부, 접수 순번·중복 요청·재시작 처리 |
| 4 | 독립 시나리오 시험, 지연/유실/중복/재시작 주입, 이벤트 로그와 통계 |

| 시험 | 기대 결과와 판정 |
|---|---|
| 양끝 동시 요청 및 같은 방향 동시 요청 | 확정 허가 하나, 실제 통로 점유 최대 한 대 |
| 1 cm 또는 검출시간 근소한 차이 | 일관된 접수 규칙 적용, 두 로봇 모두 자기 우선이라고 진입하지 않음 |
| REQUEST/GRANT/ENTER/EXIT 각각 유실 | 재시도 가능, 새 중복 소유권 없음, 불확실하면 차단 |
| 메시지 지연·중복·순서 뒤집힘 | 예전 GRANT/EXIT가 현재 허가나 점유를 변경하지 않음 |
| 허가 직후·진입 중 로봇 재부팅 | 상태 재확인 전 재진입·대체 허가 없음 |
| 점유 중 중재자/broker 재시작 | 복구 중 새 진입 차단, 기존 점유 재조정 |
| heartbeat 끊김·네트워크 분할 | TTL만으로 통로가 FREE가 되지 않음 |
| 출구에 로봇·장애물 존재 | 진입 전에 대기 또는 BLOCKED, 출구를 향해 밀어 넣지 않음 |
| 두 통로 자원 순환 | 진입 전 순환을 차단하거나 계획 불가능을 명시 |
| 후진 불가 막다른 통로 | 경로 실패를 정직하게 반환, 가짜 제자리회전/순간이동 금지 |
| 지속적인 경쟁 요청 | 정상 통신·유한 통과시간 조건에서 기아 없음; 최대대기시간/처리량 기록 |

핵심 로그는 REQUEST → GRANT → ENTER → EXIT/FAULT 순서, 현재 소유자, 실제 점유자 수, 출구 berth 상태다. 물리 점유는 이벤트 자기신고만 세지 말고 시뮬레이터의 차체-통로 교차로도 독립 측정한다. 통신 장애 동안 안전 때문에 멈춘 경우를 '완료'나 '교착 자동 해결'로 기록하지 않는다. 무조건 우회 대신 대기를 기본으로 하고, 검증된 전진 우회 경로가 있으며 예상 대기보다 합리적인 경우에만 정책으로 선택한다.

현재 미확인: 실물 로봇 폭·길이·적재물 외형, 최소 회전 반경, 제동거리, QR 인식 거리/실패율, 대기 berth 크기, 출구 구조, 통신 최악 지연과 단절 범위. 따라서 1 cm·정지선 거리·최대 처리량의 실물 수치는 산출할 수 없다.

Nav2 Collision Monitor는 로컬 충돌 정지를 위한 추가 계층이며 hard real-time 안전 인증을 제공하지 않는다고 공식 문서가 명시한다. 통로 예약과 별도로 사용하되 산업 안전이 검증되었다는 결론으로 확대하지 않는다.
