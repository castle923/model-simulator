## 결론

요구한 공장은 구현 가능성이 있다. 다만 **한 대만 통과하는 통로에서 후진·횡이동·제자리 회전을 모두 금지하면, 통로 안에서 마주친 뒤 해결하는 설계가 아니라 들어가기 전에 충돌 가능성을 제거하는 설계가 필요하다.** 로봇 전체가 빠져나갈 출구 공간까지 확보한 뒤 한 방향 통행을 허가하고, 반대편 로봇은 통로 밖 지정 대기 위치에서 기다려야 한다. 우회는 실제 전진 경로와 회전 공간이 존재할 때 선택하는 대안이다.

## 통로 폭·회전 공간·축소의 계산 방법

다음 식은 배치 검토용 기하 조건이며 안전 표준 또는 인증 기준이 아니다. `m`은 벽 이격·주행 오차·위치추정 불확실성 등을 반영해 설계자가 정하는 여유다.

- 직선 통로에서 한 대가 정확히 정렬되어 지나가는 예비 조건: `B ≥ W + 2m`.
- 동일 폭 두 대가 옆으로 교행하는 단순 예비 조건: `B ≥ 2W + 3m`(벽 쪽 두 여유와 기체 사이 한 여유를 모두 m으로 둔 가정).
- 각도 오차 θ가 있을 때 직사각형의 횡방향 투영 폭은 `W|cosθ| + L|sinθ|`. 폭만 딱 맞는 통로는 아주 작은 기체 각도 오차에도 실패한다.
- 제조사 명목 폭 `.16583m`를 적용한 교육용 계산 예: 통로 `.24m`이면 정렬 상태에서 한쪽 여유는 `(.24-.16583)/2=.037085m`, 약 37.1mm다. 이 통로 폭과 여유는 사용자의 실제 공장 안전값으로 승인되거나 검증된 것이 아니다. 위치오차·바퀴 미끄러짐·회전·짐에 따라 부족할 수 있다.
- 원호 중심선 반경 R의 180° U턴은 중심 경로만 해도 측방향으로 `2R`를 사용한다. 원형 몸체 반경 ρ를 쓰면 측방향 폭은 `2R+2ρ`에 추가 여유가 필요하다. 현재 가상값 R=.65, ρ=.22이면 이 단순 U턴의 측방향 폭만 1.74m다. 이는 실제 Raspbot 최소 요구 공간이 아니다.
- 직사각형은 순간회전중심에서 각 꼭짓점까지의 반경과, 진행 중 변환된 전체 다각형의 합집합을 검사해야 한다. `S = union_t Transform(x(t),y(t),yaw(t), footprint)`를 벽·랙·다른 기체의 점유 영역과 비교한다. 길이·폭·앞뒤 돌출·적재물 때문에 중심선 또는 반경 W/2 원만 검사하면 모서리 충돌을 놓친다.

화면 확대/축소는 표시 배율만 바꾸고 실제 m 값을 유지한다. 10×6m를 더 작은 실제 공장으로 바꾸는 일은 별개다. 지도 좌표만 1/2로 줄여도 로봇의 실제 L/W/R, 제동거리, 센서 사각지대는 1/2로 줄어들지 않는다. 현재 상수 `.22/.49/.65/1.1`, `.13` 탐색 격자 및 `.16` primitive를 자동 비례 축소하는 것은 타당하지 않다.

권장 배치는 **좁은 랙 통로 + 양끝 회전 마당 + 교통 흐름을 막지 않는 대기·작업·주차 칸**이다. 막다른 통로에 U턴 공간이 없고 후진도 금지하면 되돌아올 경로 자체가 없다. 그런 작업은 접수 단계에서 불가 사유를 표시하거나 일방통행 순환 경로를 마련해야 한다. 제조사 명목 크기에 맞춘 2×1.5m 같은 소형 연구 지도도 후보로 검토할 수 있지만, 현재 4m 하한 때문에 그대로 입력할 수 없고 수치·격자·배치 모델의 재설계가 필요하다. 전진 회전 반경과 모든 작업의 이탈 가능성 검증 전에는 그 크기에서 요구 공장이 동작한다고 보장할 수 없다. 정확한 최소 지도의 가로·세로는 회전·운용 실측값 없이 확정하지 않는다.

## 통행 예약과 통신의 설계 범위

통로를 유향 edge, 입구 대기 위치·출구 berth·회전 마당·작업 칸·주차 칸을 node/resource로 나타내는 위상 지도가 적합하다. 이를 세밀한 곡선 경로 탐색과 함께 사용한다.

1. 기체가 진입 허가를 요청할 때 통로뿐 아니라 해당 방향의 출구 berth와 전진 이탈 경로가 비어 있는지 검사한다. 통로+출구를 한 트랜잭션으로 예약하거나 모두 거부한다.
2. 허가받지 못하면 정지거리 밖의 대기 칸에 정렬하여 대기한다. 좁은 통로 안 또는 반대편 로봇의 회전 자취에 대기점을 두지 않는다.
3. 허가받은 기체가 진입·점유·꼬리 이탈을 보고한다. 후미와 적재물이 완전히 벗어난 후 통로 소유권을 해제한다.
4. FIFO/대기시간 가산 등으로 기아를 막고, 여러 자원을 요청할 때 획득 순서 또는 전체 자원 사전 확보로 교착을 예방한다. 현재 ID 우선 우회는 장시간 운영의 공정성 정책으로 충분하지 않다.
5. 통신 장애 시 lease 만료만 보고 점유된 통로를 상대 기체에 넘기지 않는다. heartbeat 상실은 점유 불명 상태이며 실제 위치·이탈 확인 또는 복구 절차가 필요하다.

요청/응답에는 robotId, taskId, resourceId, direction, sequence, requestId, mapRevision, timestamp, validity, reservation token이 필요하다. 재전송은 멱등이어야 하고 오래된 grant·release는 거부한다. 중앙 조정 서버와 기체 간 직접 통신 중 무엇을 쓰든 물리 통신 경로를 따로 검증해야 한다. 먼저 가상 메시지 버스에 지연·손실·중복·순서 뒤바뀜·단절을 주입할 수 있다.

현재 전역 poses 충돌 방지는 가상 world의 충돌 판정용 oracle로 유용하다. 그러나 제어기가 그 진실을 몰래 읽으면 센서/통신 실패 성능이 과대평가된다. 실제 controller가 보는 관측값과 simulator의 정답값을 분리하고, 충돌 방지가 개입한 횟수를 별도 표시해야 한다.

## 상시 공장·바이브 동적 작업

로봇 등록과 작업 목적지를 분리한다. 로봇은 `IDLE/PARKED/ASSIGNED/MOVING/WAITING_RESOURCE/WORKING/CHARGING/FAULT` 등의 상태로 계속 존재하고, world clock과 pose·배터리·적재·예약은 작업이 끝나도 유지한다. “모든 작업 완료”는 공장 종료가 아니라 빈 작업 큐 상태다.

사용자 문장 `R1은 작업자 1에게 안전모 1을 전달해`는 구조화 Task로 변환하여 기체 ID·대상·행동·도착/출발 방향을 미리 확인한다. 실행 중 새 작업은 append/현재 작업 후 수행/안전 위치에서 중단 중 명시된 정책으로 처리한다. R1을 지정하면 R1 큐에 넣고, 기체를 지정하지 않을 때만 가용성·배터리·예약·도달 가능성·대기시간을 보고 자동 배정한다. 파서 범위를 넘는 명령은 임의 실행하지 않고 지원 범위와 미해석 항목을 표시한다.

최소 Task에는 taskId, 요청시각, 지정기체(선택), actions, 상태, 우선순위, idempotencyKey, 실패사유, 재시도 정책이 필요하다. 같은 안전모를 두 작업이 집거나 같은 berth를 중복 예약하지 않도록 자원 소유권과 작업 예약을 함께 관리한다. 운행 도중 추가된 작업은 다른 로봇 pose·clock·payload·reservation을 초기화하지 않아야 한다.

주차는 통로 밖 전진 입출차가 가능한 공간으로 정의하고, 각 idle 기체가 예약한다. 주차된 기체도 장애물이다. 후진 금지에서는 벽을 향해 주차하면 다음 작업을 시작할 수 없으므로 주차 완료 yaw와 출발 가능 궤적도 검사한다. 빈 칸이 없으면 안전 대기 상태를 보고하며 기체를 삭제·겹치기·순간이동시키지 않는다. 충전은 모든 작업 뒤 강제로 수행할지, 배터리 정책으로 결정할지도 분리한다.

## Nav2 선택 근거와 제한

[Nav2 Smac 공식 개요](https://docs.nav2.org/rolling/configuration_and_development/configuration_guide/planners_plugins/smac/)는 Hybrid-A*를 car/Ackermann용 SE2 계획기로, State Lattice를 다양한 기구학용 계획기로 구분한다. [Smac Hybrid 설정](https://docs.nav2.org/rolling/configuration_and_development/configuration_guide/planners_plugins/smac/smac_hybrid/configuring_smac_hybrid/)에서 `motion_model_for_search=DUBIN`과 `minimum_turning_radius`를 사용하면 전진 곡률 제약을 표현할 수 있다. Reeds–Shepp는 후진을 허용하는 모델이므로 큰 reverse penalty를 주는 방식은 후진의 절대 금지와 다르다. Nav2 [공식 소스](https://github.com/ros-navigation/navigation2/blob/main/nav2_smac_planner/src/node_hybrid.cpp)는 Dubins/ReedsShepp 상태 공간 분기를 확인할 수 있다.

[State Lattice 공식 설정](https://docs.nav2.org/rolling/configuration_and_development/configuration_guide/planners_plugins/smac/smac_lattice/configuring_smac_lattice/)은 custom primitive와 reverse expansion 설정을 제공한다. 전진만 허용하려면 reverse expansion을 끄고 primitive 집합에서도 제자리 회전·횡이동을 제외해야 한다. rotation penalty는 금지 조건이 아니다. 경로 계획 외에 controller, recovery/backup/spin, docking의 동작 정책까지 같은 제약을 적용해야 한다.

이 조사는 Nav2 설치·실행 검증이 아니다. 현재 웹 TypeScript 경로 탐색은 Nav2 자체가 아니다. 위 링크는 rolling 문서이므로 Ubuntu 24.04/Jazzy의 실제 설치 패키지와 API를 별도로 확인해야 한다. Route Server라는 제품 구성 요소의 배포판 가용성/백포트도 확인하지 않았다. **통로 graph 개념은 프로젝트에서 직접 구현할 수 있지만 특정 Nav2 Route Server가 현재 환경에 설치되어 바로 사용 가능하다고 주장하지 않는다.**

## 유리·곡면·초음파·LiDAR 실패

| 현상 | 공식 근거 | 시뮬레이터에 반영할 것 |
|---|---|---|
| 매끈한 면의 비스듬한 초음파 반사 | [Pepperl+Fuchs FAQ](https://blog.pepperl-fuchs.com/en/2018/ultrasonic-sensor-faq-detection-range-and-accuracy/)는 평면이 센서 축에 수직일 때 최대 검출 범위이며, 매끈한 면·작거나 둥근 물체·반사 방향에 따라 범위가 줄어듦을 설명 | 입사각/거리/크기별 반사 손실, no-return. 투명도와 별도로 곡면의 국소 법선이 변화하는 효과 |
| 표면·각도·흡음재·초음파 간섭 | [OMRON E4PA-N 자료 p.6](https://www.ia.omron.com/data_pdf/cat/e4pa-n_ds_e_5_4_csm1404.pdf)은 표면·각도 제약과 흡음/시험 필요성을 설명하며, 해당 제품의 상호 간섭 방지 연결은 측정시간도 늘림 | 로봇 2대 이상 동시 발신 간섭·측정 지연·사각거리. 해당 산업용 센서의 수치를 Raspbot 센서 사양으로 가져오지 않기 |
| 유리 전면·뒷면 물체가 LiDAR에 섞임 | [Hokuyo multi-echo 설명](https://www.hokuyo-aut.jp/products/data.php?id=121)은 유리 등에서 투과 전후의 복수 반사가 발생할 수 있고 echo 선택이 영향을 줌을 설명 | 앞 유리 무검출, 뒤 벽 거리 반환, 여러 echo, 각도별 간헐 검출. 가장 먼 echo를 빈 공간 증거로 오인하는 사례 |
| 투명물 전용 광센서도 설치 조건 필요 | [SICK WLG 공식 기술 문서](https://support.sick.com/sick-knowledgebase/article/?id=360e1068-20e1-45fa-9f9e-37959ecb3153)는 sensor-reflector 고정 쌍, 재학습, 진동·거리 변경의 영향을 설명 | 환경에 표지/반사체를 설치한 접근은 후보이나 이동식 로봇 센서 하나가 모든 투명체를 해결한다는 의미가 아님 |

`no-return`은 장애물 없음과 같지 않다. 기존 지도에서 유리벽이 확인되었다면 한 번의 무반사로 그 벽을 free로 지우지 않는다. 지도 사전정보, 다른 방향 관측, 카메라·거리센서 융합, 설치 표지 등을 사용할 수 있지만, 각 센서가 같은 조건에서 동시에 실패할 가능성도 남는다. 불확실 영역에서는 감속/진입 보류/재관측으로 연결한다. 센서 fusion으로 모든 투명·곡면 물체가 해결된다고 보고하면 안 된다.

현재 `scene-sensor.ts`의 visible empty old position 즉시 제거와 TTL은 합성 기체 track 처리다. 실제 유리벽 mapping이나 물리 센서 ghost 제거를 증명하지 않는다. 광선이 가상 사각형을 확실히 맞히도록 그렸다는 사실도 실제 유리 검출 성능과 다르다.

## 최소 검증 시나리오 제안 — 아직 실행하지 않음

두 개 이상의 독립 작업을 같은 살아 있는 공장 세션에 넣고 다음을 기록해야 한다. 아래는 향후 검증 계획이며 통과 결과가 아니다.

## 다음 작업을 구체화할 순서

1. 실측 RobotProfile과 운용 제약을 확정한다. 정확한 최소 지도 크기는 이 단계 이후 계산한다.
2. 랙 직선 통로·입구 대기·출구·회전·작업·주차 자원을 설계하고 모든 상태에서 전진 이탈 가능한지 검토한다.
3. 정적 지도와 상시 WorldState/RobotState/TaskQueue/ReservationState를 분리한다. 임무 투입이 map commit/전체 reset을 부르지 않게 한다.
4. 발진·제동·직사각형 회전 자취와 통로+출구 예약을 먼저 검증한다. 그 뒤 공간이 있는 경우에만 동적 우회를 연결한다.
5. 최소 두 작업의 연속 처리와 통신/센서 고장을 재현하고 독립 검토한다. 웹 검증, Gazebo/ROS 검증, 실제 Raspbot 시험 결과를 별도로 남긴다.

연구 완료 범위는 이 보고서의 코드 대조·공식 자료 확인·설계 제안이다. 기능 구현, 물리 주행, 센서 성능, 운영 배포 또는 위 시나리오 통과는 이번 작업의 완료 항목이 아니다.
